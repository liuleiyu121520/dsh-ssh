## dsh 桌面端启动崩溃修复（web boot: dsh-ssh-terminal: failed）
- 根因：cordis 4.x 访问**未在 inject 声明**的服务属性会抛 `cannot get property "X" without inject`（不是返回 undefined）。`src/client/launchpad.js` 的 `const locale = ctx.locale` 让客户端 apply 炸掉 → fiber FAILED → 整个 app 起不来。
- 修法：`ctx.locale` → `ctx.get('locale')`（非抛访问器）；**不能**把 'locale' 加进 inject（服务缺失会变 pending，同样激活失败）。commit 8b39f7b。
- 定位手段：node 复现 harness（真 cordis + 真 cordis-plugin-loader + 真 client-modules + vm sandbox 加载真 lib/client.js），已固化为 `scripts/client-boot.repro.mjs`（退出码 0 = 激活通过）。教训：仓库既有单测全跑假 ctx 替身，这类真机崩溃单测永远抓不到。
- 验证：85/85 单测、repro 正负对照、真机 `open -a "DeepSeek Harness"` 冷启动 4 分钟零新崩溃日志。

## 右栏 AI 助手（对话驱动 SSH 终端）—— commit 8949b6d
- 需求：右栏不要静态上下文卡，要能对话、能读面板、能生成并执行命令的助手。
- 架构：Host `src/chat.js` 只经 `ctx.get('llm')`（cordis 服务名 llm，LlmRuntime）调宿主模型，**不 import dsh 内部包**；无状态回合（客户端每轮 POST 完整 history），人工确认/自动执行双模式；`run_command` 工具经 marker 回显捕获输出。
- 新端点：GET /llm、POST /chat（SSE）、POST /chat/exec（前缀路由）；`ctx.inject(['llm'])` 分层挂载，缺 llm 降级不炸。
- 客户端 ChatPane.jsx 全重写：流式消息、命令卡（执行/跳过）、模型下拉、自动执行开关；store.js 加 chats 状态机 + fetch SSE 读取。
- 验证：npm test 100/100；scripts/chat-e2e.mjs（真 ssh 120.53.14.173 + 真 llm 包 + 假 adapter）12/12；client-boot.repro 激活回归过。
- **两个真机才发现的坑（单测全绿也抓不到）**：
  1. marker 正则要求 `(?:^|\n)` 开头 → 真终端 marker 行前是 `\r`（bracketed paste `\e[?2004l\r` 包装），永远匹配不上，表现"输出全有了却超时"。改为"marker+码+行尾即中"。
  2. 手搓 assistant 消息缺 `source` → 真 runtime `forAdapter()` 读 `source.replayState` 直接 TypeError，被包装成终态 finish，表现"模型静默结束"。assistant 消息必须补 `{kind:'model',provider,model}`。
- 真终端环境事实：OpenCloudOS bash 开着 bracketed paste；prompt 带 OSC 标题序列；行尾 \r\n。

## 修复：prepared LLM call config changed before adapter dispatch —— commit 07ae69e
- 真机症状：右栏发消息即报此错（GLM-5.3 真 provider）。
- 根因：`LlmRuntime.prepareCall().stream()` 分发前做 `callConfigEquals`（比 provider/model/reasoningEffort/temperature/maxTokens/stop），我只传了 provider+model，漏掉 adapter 物化的默认值（free-model adapter 给 GLM-5.3 物化 reasoningEffort）→ INVALID_PREPARED_CALL。
- 修法：stream 入参 `...prepared.config` 原样带回。
- 为什么 E2E 没抓到：E2E 假 adapter 的 modelInfo 没有 effort 默认值，resolvedConfig 恰好等于入参。改用严格契约假 llm（prepareCall 物化 reasoningEffort:'high'，stream 校验一致性）后旧实现必炸。

## 修复：finish reason 形状错误导致“输入了没反应” —— commit（本轮）
- 真机症状：发消息后用户气泡在，助手侧零响应、无错误、无“思考中”。
- 根因：真 adapter 的 finish chunk 是**对象** `{kind:'error', failure:{message,code}}`（dsh-llm types.ts FinishReasonMap），我按字符串解析 → 错误 finish 被当成正常 stop 吞掉 → runTurn 走“无工具调用→finish stop”静默路径，而 model/finish 事件在 UI 上都不可见 → 看起来完全没反应。
- 附带修复：零文本零工具的空响应也发 error 事件（empty-response）；对话半层 llm capture 改 `scoped.llm ?? scoped.get('llm')` 双保险（属性访问走 fiber 链、get 走 context store，作用域可见性不同）。
- 教训：测试里的 chunk 形状必须照真契约写——前两轮测试用字符串 reason 所以全绿，真机第一次跑就栽。
