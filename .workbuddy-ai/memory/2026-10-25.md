## 接上启动台 onTeardown（v1.2 新协议）
- 用户提示：启动台协议变了，关卡片会通知插件销毁。核实 `dsh-launchpad/src/page.js`：`viewProps = {appId, app, close, onTeardown, open, t, active}`；`onTeardown(handler)` 返回注销函数，handler 收 `{reason}`，**同步**执行；触发点 = `closeTab()` 第一步（用户点 ✕ 或插件自己 `props.close()`，reason `tab-closed`）与启动台整体卸载（reason `launcher-disposed`）。
- 此前本插件完全没接（SshAppView 连 `active` 都丢给 `_active`）→ 关卡片只是看不见，Host 侧 SSH 连接、客户端 xterm + EventSource 全成孤儿。
- 实现：`store.teardownAll(reason)`——同步：stopPolling + 逐 sid `destroyRuntime()`（ES/xterm/DOM 全收）+ 状态归零（tabs/activeSid/sessions/chats）；异步：逐个 `POST /close` fire-and-forget（协议要求 handler 同步返回，关闭动画不能等 HTTP）。App.jsx 用 `useEffect` 注册，老启动台不传该 prop 时防御性跳过；顺带把 `active` 用对（隐藏停轮询、显示再开，两个函数都幂等）。
- 测试 154/154：新增 tests/store-teardown.test.js 4 条（每会话一次 /close、状态归零、轮询停、幂等）；jsdom 端到端（/tmp/mdcheck/run4.mjs，模拟启动台调 handler）验证注册与关闭请求。
- 坑：测试里 openSession 依赖 /open 返回 sid，桩漏了会静默失败（showToast 后 return null，tabs 不建）。

## 修复：不再自动开标签 + 连不上时把原因写进终端
- 用户报两件事：①第一次进 SSH 卡片就自动多出「腾讯云 #1」标签；②"双击连接不上了"（截图里终端全黑）。
- **①的根因是配置合并语义**：`autoOpenFirst` 写成 `=== false` 才跳过；而 profile 的 `~/.dsh/profiles/desktop/cordis.patch.yml` 里 `- id: dsh-ssh-terminal / config: {enabled: true}` 会**整块替换** config（vendor/include/src/index.ts 的 applyEntryPatches 就是 `target[key] = value`，不是深合并）→ bundle patch 的 `autoOpenFirst: false` 被抹掉 → 字段缺席 → 自动开。改成 `!== true` 才生效。**通用教训：dsh patch 的 config 是替换不是合并，默认值必须落在安全侧。**
- **②不是插件 bug**：真机 `/open` 200、会话状态 `error: Connection lost before handshake`。裸 socket 探针（python）：TCP connect 1-5ms 成功，之后 **~5.0s 收到 FIN、零字节 banner**；系统 `ssh -v` 同样 `kex_exchange_identification: Connection closed by remote host`；ping 通、80/443 通 → 服务端/云安全在拦本机 IP（典型 fail2ban 类爆破保护），需在服务器侧解封。
- 但暴露了产品缺陷：SSH 失败时缓冲零字节，客户端收到 `event: exit` 只 close()，黑屏静默 → 用户以为卡住。现 store.js 新增 `writeFailure()`：exit 帧带 reason 就写红字「✗ 连接失败：<reason>」，首屏失败（rt.seq===0）再补一行排查提示。
- 顺带对齐双击语义（注释本来就这么写）：`handleOpenTab` 先找该主机 open/connecting 的会话，有就聚焦、没有才新建；行内 `+` 改走新的 `onNewTab`（总是新建），两者不再混用。
- 验证：单测 159/159；client-boot.repro 通过；假 ssh2 服务端（/tmp/dsh-ssh-diag2.mjs，进程内 ssh2.Server + 假 shell）端到端确认「激活后会话=0」且连接成功时 SSE 真出字（`FAKE_SHELL_READY\r\n$ ECHO HI`）。

## 多轮工具循环的渲染顺序（正文/命令卡错位）
- 症状（用户截图）：一个回合跑了四轮命令，右栏是一整篇结论在最上面、四张命令卡全堆下面，最新那句被顶出可视区。
- 根因：auto 模式下 Host 在**一次** `runTurn` 里循环多轮（`chat.js` 的 `for (round < MAX_TOOL_ROUNDS)`），只发一个 `finish`；客户端把所有流式增量并进同一条 turn 消息（`{text, calls}`），`TurnMessage` 又是先 text 后 calls → 顺序必然是"全部正文 + 全部卡片"。
- 改法（对齐原生：一个 assistant 消息 = 一次模型响应）：Host 每轮工具执行完发 `{type:'round', replayState}`；客户端 `handleChatEvent` 收到 round 就把当前 turn 封口（streaming=false + 落 replayState），下一段另起一条消息；`TurnMessage` 新增 showLabel，连续 turn 只在第一条显示"助手"。
- **关键坑**：replayState 必须**按轮**发，不能只留最后一轮那份——每轮的思考签名属于各自的模型响应，`buildChatHistory` 按消息取签名，缺了就是 2026-10-24 那个"续轮必挂"。
- 验证：163/163（chat.test.js 事件序列补 round + 断言边界位置；新增 tests/store-chat-rounds.test.js；jsdom run9.mjs 核对 DOM 顺序严格递增、"助手"只出现一次）。
- 提交 95b2492。

## rz/sz：浮层不出现 + Ctrl+C 退不出
- 症状（用户截图）：终端里刷出 ZMODEM 乱码字节，没有选文件的浮层；连按 Ctrl+C / Ctrl+X 都退不出去。
- **浮层根因（我的 bug）**：`/transfer/events` 复用了终端字节流的 `formatSseFrame`，把 `{type:'transfer',phase:...}` 当成 `{seq,chunk}` 打包 → 两个字段都取不到 → `JSON.stringify` 吐出 `{}`，客户端只收到两个空对象，`handleTransferEvent` 一律忽略。诊断脚本打原始帧才看到 `[diag] 传输事件 = [{},{}]`。新增 `formatEventFrame`（原样序列化事件对象），`formatChatFrame` 改成它的别名，传输事件走新函数。**通用教训：SSE 只有一种线格式，但"业务事件"和"终端分片"是两种 payload，别共用打包函数。**
- **Ctrl+C 退不出的根因**：rz/sz 启动即把 pty 切成 raw 模式，0x03 不再产生 SIGINT，ZMODEM 也不认它。真正能打断的是**连续 CAN(0x18)**。本机实测（python pty 桥 + 真 lrzsz）：发 5 个 CAN 不够（rz 重试 10s 不退），发 8 个 0.9s 退出（exit 128）→ 定 `CANCEL_BYTES = 10` 留余量。
- 落地：`transfer.cancel(sid)`（发 CAN + emit cancelled/end + settle，**没有进行中的传输直接 return false**，否则会往正常 shell 灌噪音）；`transfer.interceptInput(sid, bytes)` 把传输期的 Ctrl+C 翻译成 cancel（Xshell 的行为），`/input` 命中就先返回 `{cancelled:true}` 不再写 PTY；新增 `POST /transfer/cancel` 给浮层的「取消」按钮。
- 客户端：`watchTransfer` 的 end 分流——只有 `complete` 留 4 秒展示，cancelled/error/空转立刻清（否则浮层变空盒子）；`TransferBar` 用 `KNOWN_PHASES` 白名单过滤，未知 phase 和 `end` 直接 return null。
- 验证：169/169（routes 新增 3 条：传输事件是原始对象不是 `{seq,chunk}`、传输中 Ctrl+C 走取消且不写 PTY、`/transfer/cancel` 转发；transfer 新增 3 条：cancel 发整串 CAN 并摘出传输态、无传输时 cancel 是空操作、Ctrl+C 被翻译成取消）。client-boot.repro 通过。
- 真机验证仍需用户重启桌面端（app 加载 lib/，已 `node scripts/build.mjs` 重建，432725B / 81.3% 预算）。

## 空对话时输入区垂直居中
- 用户要求：AI 对话进来没内容时 input 垂直居中，发过消息才落到底部。
- 原生对照：`packages/client/ui-conversation/src/client/skeleton/HeroShell.module.css` 的 `.root { height:100%; align-items:center; justify-content:center }` —— 标题在上、composer 在下、**整组**居中（不是 composer 自己绝对居中）。注意 EmptyHero.tsx 顶部注释：composer 留在 ConversationRoot 里，就是为了切态不重挂 textarea。
- 实现（ChatPane）：aside 里消息区上下各加一个弹性占位，空对话（无消息 + 不在跑 + 无 error）时两个占位 `flexGrow:1/flexBasis:0`、消息区 `flexGrow:0`；有消息后占位归零、消息区 `flexGrow:1`。占位节点**始终存在**只换数值 → composer 兄弟位置不变 → textarea 不重挂，草稿不丢。
- 坑一：`style.flex = '1 1 0'` 这种简写要过 cssstyle 语法解析，无单位 basis 会被丢掉（jsdom 里读回来是空串）。改用 flexGrow/flexShrink/flexBasis 长写。
- 坑二：空对话不再调 `scrollIntoView`（原来 mount 就滚），居中态会去滚启动台外层容器，进来页面跳一下。
- 坑三（测试）：受控 textarea 直接赋 `.value` + dispatch input 不会触发 React onChange（value tracker 认为没变）。要用 `Object.getOwnPropertyDescriptor(HTMLTextAreaElement.prototype,'value').set.call(node, text)` 绕开。
- 验证：jsdom（/tmp/mdcheck/run10.mjs，esbuild `--loader:.js=jsx --jsx=transform` 重打 chat.mjs）核对 6 条：空态占位 grow ["1","1"]/消息区 "0"、草稿写入、发送后占位 ["0","0"]/消息区 "1"、textarea 同一节点、草稿仍在、回复已渲染。全量 169/169；client-boot.repro 通过。
