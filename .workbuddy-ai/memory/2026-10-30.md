## 热更新后右栏对话整段消失（会话不对称）

- 症状（用户真机）：AI 正在跑任务时我热更新了客户端，控制面板还在跑，但右栏对话没了；终端好好的。
- 根因：**终端和对话的持久化位置不一样**。终端字节流在 Host 的 `sessions.js` 滚动缓冲里，客户端重挂载自动回放（`since=rt.seq`）；而对话历史按设计只活在客户端 `state.chats`（chat.js 头注释：Host 是无状态回合，每轮 POST 完整 messages），模块一重新求值就归零。
- 这次丢掉的内容**无法找回**：`~/.dsh/logs` 只有一个启动日志、`~/.dsh/llm-deepseek` 只有 files-v3.json，没有请求正文；Host 侧也没存。只有终端滚动缓冲里还留着 AI 跑过的命令与输出。
- 修复（`src/client/chatStore.js` + store 接线）：按 sid 把 messages 存进 **sessionStorage**（不是 localStorage：命令输出可能带敏感信息，不该长期落盘；每标签一份也不会互相覆盖）。节流 400ms 写、回合结束（`streaming:false`）立即 flush；40 条 / 160KB / 8 个会话封顶；quota 满先淘汰旧会话，再失败就放弃——持久化是锦上添花，不能打崩右栏。
- 恢复时三个必须做的动作（少一个都会出问题）：
  1. **封口**：`streaming` 的回合标 `interrupted` 并清 streaming，否则永远转圈；ChatPane 显示「这条回复被中断了」。
  2. **补 tool 结果**：`status:'running'` 且没有 `resultContent` 的命令改 `failed` + 一条「结果未知」，否则 `buildChatHistory` 会产出"有 tool-call 没有 tool 结果"的 history，下一轮被 wire 校验打回。
  3. **重推 pending**：判据与 `resolveToolCall` 末尾一致（还有没有没归属的 tool-call），恢复后能直接点「执行」续跑。
- 清理：`closeSession` / `deleteHost` 调 `forgetChat(sid)`（内存 + 存储 + 待写队列一起摘）。
- 验证：187/187（新增 `tests/chat-store.test.js` 10 条）。真 Chromium（/tmp/sshcheck，stub 里加了 `/llm`、`POST /chat` 的 SSE 帧、`/chat/exec`）：发消息 → `page.reload()` → 对话、待确认命令卡、pending 提示都在，点执行能续跑；再造一条 streaming 历史 → 重载后 interrupted/failed/「结果未知」全对。
- 提交 3f3299c。

## 点完「执行」后输入框永久锁死（混合批次）

- 症状（用户截图）：AI 提示一条危险命令，用户同意并执行，命令跑完、输出也在卡片里，但之后输入框一直锁着，底部提示「先处理上方的命令卡（执行或跳过）」，而屏幕上已经没有待处理的卡片。
- 根因两条，缺一条都复现不出来：
  1. 一个批次里**自动执行**的命令由 Host 发 `tool-result` 事件（chat.js 的 `emit`），客户端这条分支只写了 status/output，**没写 `resultContent`**；
  2. `resolveToolCall` 用「还有没有 `resultContent === undefined` 的 call」判断 pending → 那条自动执行的卡片永远算没归属 → pending 永远为真 → 不续跑 → `ChatComposer` 的 `locked = streaming || pending` 把输入框锁死。
- 关键洞察：**pending 必须看卡片状态（awaiting / running），不能看"有没有结果"**。结果字段是 history 的产物，状态才是"等用户处理"的语义。判据写错一次，UI 就变成没有任何出口的死局。
- 改法：Host 的 `tool-result` 增加 `content`（进 history 的全文 6000 字上限），`output` 保持人看的预览 1200 字；客户端写 `resultContent`/`resultError`；抽 `hasOpenCall` 按状态判 pending，最后一张卡处理完显式 `patchChat({pending:false})` 再续跑（别指望 runChatTurn 开头那句兜底——它被并发守卫挡掉时就是死局）。
- 顺带修恢复路径：`chatStore.restoreChatState` 也按状态判 pending，并给「已落终态却没有结果」的旧卡片用 output 补一条结果——否则旧历史重载后，下一轮 history 会因 tool-call 缺结果被 wire 校验打回。
- 验证：190/190。新增 `tests/store-chat-approval.test.js`（混合批次点执行/跳过都必须解锁 + 续跑 + history 里每个 tool-call 都有 tool 结果）。真 Chromium：`/tmp/sshcheck/repro.py` 修前 pending=true，修后 false 并续跑出「全部检查完了」；`rescue.py` 造旧格式历史重载 → 卡片结果被补上、输入框可用（**用户当前卡住的那段对话，热更新后会自动解锁**）。
- 提交 1270b93。




## 「存储不可用：当前未启用持久化主机表」= 热更新泄漏了域句柄

- 症状（用户截图）：左栏只剩一台 patch 只读主机（标签是 `root@120.53.14.…` 而不是库存里的「腾讯云」），点添加主机弹「存储不可用」。
- 诊断手法（可复用）：写脚本用**真实 dsh 存储栈**开一次域，确认插件侧没问题——
  `new Context()` + `ctx.plugin(storageMod.default)` + `{name,apply,inject,Config}` 形态挂 `dsh-storage-json`/`dsh-storage-domain`，
  再用 `defineDomainSpec()` 去 open。结论：拿 `~/.dsh/storages/dsh_ssh.json` 的真实数据能正常打开并 `get()` 出记录 → schema/spec 没问题。
  顺带确认 `~/.dsh/storages/workspace.json` 今天还在写 → 存储栈本身是活的，坏的只有 dsh_ssh 这一个域。
- 根因：`HostStore` 从不 `close()` 域句柄；`DomainFacility` 按域名字登记，重复 open 抛 `already-open`。
  插件热更新（改 lib/ 后宿主重挂）每次都新建一个 HostStore → 几次热更新之后 dsh_ssh 再也打不开，只有重启应用能恢复。
- 修法：`HostStore.close()`（释放句柄、清表引用、吞掉异步 rejection）；持久化半的 disposer 先 close 再 forget DEK；
  init 失败也 close 半开状态并把原因码记进 `state.storageError`；`GET /hosts` 返回 `storage:{ready, reason}`，
  客户端把原因拼进提示且**只在原因变化时弹一次**（2s 轮询不守卫会一直重弹）。
- 测试：fake storageDomain 现在**忠实复现 already-open**（重复 open 抛、close 释放），新增两条用例锁住这个行为。
  连带修了 hosts.test.js 里"改库换密文"那条：它原来靠重复 open 模拟攻击，现在改走 `store.domain.table()`（真设施也不允许重复 open）。
- 提交 ccbad2b。

  `at` / `after_seconds` / `every_seconds` / `daily{time,time_zone}` / `weekly{time,time_zone,weekdays}` / `cron{expression,time_zone}`。

- **坑**：`parseToolArgs` 只返回 `{command, timeoutMs}`，别的工具拿不到参数（第一次跑出来是"title 不能为空"）——加了 `raw` 字段。
